# Windows setup (HWDER Setup.exe)

Merged (one-button flow, R7, 2026-10-22; see [windows-setup-ux.md](windows-setup-ux.md)). Windows only. Players get it in the setup zip `HWDER-setup-<version>.zip`. The exe is not code-signed, so Windows SmartScreen may ask for confirmation (More info > Run anyway). The native window opens before Python exists and contains no game code. Real preparation and gameplay have been completed on the maintainer's PC; other machines and graphics correctness are covered by playtests, not by this tool.

Extract the complete kit and open **HWDER Setup.exe**, keeping its source folder beside it. One main button leads through Next, Install, Prepare and Play; the Data folder and every secondary action sit under **Advanced**. Choose the Data folder before installing tools. It contains private tools, generated/build stages and `play/` with the executable, settings and saves. The default is Local AppData/HWDER. Existing CLI users may select their older Local AppData/hwder/local-build-v1 root to reuse its data; the wizard does not migrate folders automatically.

1. **Next** opens the pickers for your own supported NSP and prod.keys files. The window records paths only, never copies keys, and never includes game inputs in a release. Picked paths and the Data folder are remembered across runs.
2. **Install** (shown while the Data folder has no private tool certificate) displays explicit network/size/ownership consent, then downloads eight fixed SHA-256 artifacts from python.org, GitHub and PyPI: CPython3.13.16 embedded x64, LLVM-MinGW20260908 UCRT x64, CMake3.31.12, Ninja1.13.2 and four pinned Python wheels. No administrator access, registry/global PATH change, pip, venv or system developer installation is required. Full component notices remain with downloaded tools. Installation reports real checksum, extraction, package preparation, import-check, file-hash and finalization phases. Archives already in the Data folder's download cache are reused, so a second kit location re-extracts without downloading again.
3. **Prepare** runs the checks itself: every private tool file is verified, then the established first_run backend validates the supported module hashes, generates code and builds locally. The progress line shows "Step k of 6", the stage, and during the build the Ninja file count with a remaining-time estimate measured from the actual rate. Verified work is reused. Private GNU objects have a distinct ABI/tool/source identity and are never mixed with MSVC objects. **Check requirements** under Advanced is the same verification without preparing anything; it never downloads.
4. Before updating the playable executable, the UI acknowledges the publication boundary. Cancel/Close waits during that short transaction. A failure shows one plain sentence with the next step (the full detail is under Advanced, Details) and turns the main button into Retry, Install or back to the file pickers as appropriate. This handles normal cancellation, not a promise of crash/power-loss atomicity.
5. **Play** verifies only the small private interpreter certificate and required source helpers, then explicitly verifies the playable certificate and original input paths. Managed output must have only Windows system DLL imports and the expected stack/ASLR contract; gameplay gets Windows-only PATH. Preparation never auto-launches. Ready shows **Create desktop shortcut** and **Add to Steam** beside the main button, and the installed executable under Advanced with Open game folder. Add to Steam appends a non-Steam shortcut (the installed exe, its folder as start directory) to `userdata/<account>/config/shortcuts.vdf` of the most recent Steam login, keeps the previous list as `shortcuts.vdf.hwder-backup`, never adds the same exe twice, and refuses while Steam runs, since Steam writes its list back when it closes. Original NSP/key PATHS are atomically stored in the installed game settings; no inputs are copied and other settings are preserved. The shortcut targets the installed game with its working directory, so the extracted setup kit and private toolchain are not needed to play. Keep the original NSP/keys at their selected locations. Reopening Setup quickly verifies the existing prepared certificate without checking all compiler files and lands on Play. Play is unavailable while that exact game is running, and returns after exit. Close Setup freely after launch; it does not own or terminate the game.

Windows10/11 x64, an AVX2 CPU, Vulkan1.2 driver and Windows Media Foundation are still game requirements. Windows N editions may need the Media Feature Pack; this tool does not install OS features. Network access is required only for consented tool downloads. Existing compiler installations are neither modified nor required by the private path.

## Isolation and packaging

The system PowerShell/.NET helper verifies/extracts the first interpreter. The isolated interpreter installs a separately certified complete stack and wheels without pip. Strict ZIP names, case collisions, links/reparse points, file counts/byte budgets, owned staging and per-file hashes are checked; incomplete output never becomes an active toolset. No Windows SDK redistribution is assumed: LLVM-MinGW supplies its own Windows headers/import libraries under its retained notices.

The release kit contains public source, pinned third-party source/notices and exactly one certified game-free setup executable. It includes applicable notices for statically linked bootstrap runtimes. No Python/compiler binaries, wheels, game-linked executable, generated guest C, keys, saves or private shader caches are bundled. Downloaded tools and generated code remain private in the chosen Data folder.

The original installed-Python/Visual Studio CLI remains unchanged unless explicitly given a managed toolchain by the bridge. [Legacy developer flow](local-build.md).

## Evidence and limits

Eight pinned download/extract transactions and private AES/LZ4 imports passed. All17,292 installed files match the certificate and reference traversal; no measured hashing speedup is claimed. Selected production units and four public generated-C/Windows-ABI/cache tests passed. The native setup was compiled using the private compiler; actual normal Check passed with Windows-only PATH, missing tools refused without payload creation, and synthetic preparation tested Job cancellation, nonce/spoof rejection, retry, input invalidation, publication ACK/deferred close and rendered controls. Preview never prepares or launches a game.

The full runtime/static-SDL synthetic-guest link probe is a separate NOT-A-GAME artifact, never executed or packaged; its result is tracked in the workspace owner note. It cannot certify a real game. The full public runtime/static-SDL link passed with the private compiler and only OS/UCRT imports; its synthetic executable was not run. Full clean-machine/real NSP preparation, gameplay, signing and distribution remain pending. Tests/evidence are retained under runs/managed-checks and runs/setup-preview-* in the unmerged worktree.

Do not replace an open setup or running game. An update at the existing canonical extracted-kit path retains its private-tool identity and existing prepared game; a different extraction path can select another tool identity. The setup never changes save_dir during launch-path repair.
